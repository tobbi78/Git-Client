Architektur-Überblick

Git-Client ist eine native macOS-App auf Basis von SwiftUI und Swift Concurrency (async/await). Die Codebasis folgt einer strikten Schichtenarchitektur: 

Views (SwiftUI)
  └─ ViewModels  (@Observable, @MainActor)
       └─ Services  (actor-isoliert)
            └─ GitCore  (GitRunner, GitError)

Actor-Isolation

Das Build-Setting SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor stellt sicher, dass alle Typen ohne explizite Annotation automatisch auf dem Main Actor laufen — ein klarer Sicherheitspuffer gegen Data Races in SwiftUI-State-Updates.

  • Views — reine SwiftUI-View-Structs, kein direkter Datenbankzugriff.
  • ViewModels — @Observable @MainActor final class; halten den UI-Zustand und delegieren I/O an Services.
  • Services — actor; führen git-Kommandos und Parsing durch.
  • GitCore — actor GitRunner als einziger Eintrittspunkt für git-Subprozesse; GitError als typisierte Fehler-Enum.

Statische Properties, die aus non-isolated Kontexten (z.B. actor) aufgerufen werden, tragen die Annotation nonisolated (z.B. GitLogParser.formatString, CommitGraphBuilder.laneColors).

GitRunner GitCore/GitRunner.swift

actor GitRunner ist der zentrale async-Wrapper um Foundation.Process und Pipe. Er startet git-Subprozesse, liest stdout/stderr asynchron aus und liefert das Ergebnis als GitResult zurück. 

struct GitResult {
    let stdout:   String
    let stderr:   String
    let exitCode: Int32
}

Kernmethoden

MethodeVerhalten
run(_:workingDirectory:) Führt git mit den gegebenen Argumenten aus; gibt immer ein GitResult zurück (wirft nicht).
runOrThrow(_:workingDirectory:) Wie run, wirft GitError.gitFailed bei Exit-Code ≠ 0; gibt den reinen stdout-String zurück.

Design-Entscheidungen

  • Das actor-Modell garantiert serielle Ausführung aller git-Kommandos — kein manuelles Locking nötig.
  • Statt eines geteilten Process-Pools wird für jeden Aufruf eine eigene Process-Instanz erstellt; das vereinfacht Fehlerbehandlung und Cancellation.
  • App Sandbox ist deaktiviert (ENABLE_APP_SANDBOX = NO), damit Process auf beliebige Verzeichnisse zugreifen kann.

GitService Services/GitService.swift

actor GitService bietet typisierte Git-Operationen für ein einzelnes Repository. Er kapselt GitRunner und liefert fertige Modelle zurück.

Methodegit-KommandoLiefert
loadCommits(limit:skip:) git log --all --date-order --pretty=format:… -<limit> [--skip=<skip>] [Commit]
loadBranches() git for-each-ref refs/heads refs/remotes [Branch]
loadTags() git for-each-ref refs/tags mit
%(*objectname:short)-Deref		 [GitTag]
loadDiff(sha:) git show --format= --patch <sha> CommitDiff
aheadBehind() git rev-list --left-right --count @{upstream}...HEAD (ahead: Int, behind: Int)?

Annotierte Tags korrekt auflösen

Bei annotierten Tags liefert %(objectname:short) den SHA des Tag-Objekts, nicht des zugehörigen Commits. Das Format-Feld %(*objectname:short) liefert bei Dereferenzierung den Commit-SHA. parseTags bevorzugt den Deref-SHA (falls nicht leer), sodass GitTag.targetSha immer auf einen Commit zeigt.

Parser

GitLogParser Services/GitLogParser.swift

Verarbeitet die rohe Ausgabe von git log --pretty=format:… in eine Liste von Commit-Objekten.

  • Feld-Trenner: U+001F (ASCII Unit Separator \u{1f}) — innerhalb eines Records.
  • Record-Trenner: U+001E (ASCII Record Separator \u{1e}) — zwischen Commits. Dieser Trenner funktioniert auch bei mehrzeiligen Commit-Nachrichten zuverlässig, da Zeilenumbrüche in der Nachricht keinen neuen Record starten.
  • Felder pro Record: SHA (lang), SHA (kurz), Parent-SHAs (leerzeichen-getrennt), Autor, E-Mail, Unix-Timestamp, Ref-Namen, Betreff.

DiffParser Services/DiffParser.swift

Verarbeitet die Ausgabe von git show --format= --patch <sha> in eine CommitDiff-Struktur: 

CommitDiff
  └─ [FileDiff]
       ├─ header: String          // "diff --git a/… b/…"
       ├─ fromFile / toFile
       └─ [Hunk]
            ├─ header: String     // "@@ -L,N +L,N @@"
            └─ [DiffLine]         // .context / .addition / .deletion

Commit-Graph-Algorithmus

CommitGraphBuilder Services/CommitGraphBuilder.swift

Berechnet für jede Commit-Zeile die Lane-Zuweisung sowie alle Kanten, die gezeichnet werden müssen. Das Ergebnis ist ein Array von GraphRow.

Datenstrukturen

struct GraphRow {
    let commit:    Commit
    let lane:      Int           // welche Spur dieser Commit belegt
    let laneCount: Int           // Gesamtzahl aktiver Spuren in dieser Zeile
    let incoming:  [GraphEdge]   // Kanten obere Zeilenhälfte  (0 → midY)
    let outgoing:  [GraphEdge]   // Kanten untere Zeilenhälfte (midY → height)
    let color:     Color
}

struct GraphEdge {
    let fromLane: Int
    let toLane:   Int
    let color:    Color
}

Algorithmus (Schritt für Schritt)

Der Builder iteriert chronologisch umgekehrt (neuster Commit zuerst) durch die Commit-Liste und pflegt ein Array activeLanes: [String]: activeLanes[i] enthält den SHA, den Lane i als nächsten Commit erwartet. Ein leerer String markiert eine freie Lane.

  1. Lane-Zuweisung:
    • Ist der SHA dieses Commits bereits in activeLanes? → Lane ist bekannt (Kante von oben).
    • Gibt es eine freie Lane (leer)? → Wiederverwendung (neuer Branch-Abzweig).
    • Sonst: neue Lane am Ende anhängen.
  2. Incoming-Kanten (obere Hälfte, aus dem unveränderten activeLanes-Snapshot vor der Mutation berechnet):
    • Belegte Lane i erwartet diesen Commit → Kante i → lane (Konvergenz, auch bei Merges mit mehreren einlaufenden Lanes).
    • Belegte Lane i erwartet einen anderen Commit → Durchlauf-Kante i → i.
  3. Outgoing-Kanten (untere Hälfte, nach der Mutation):
    • Alle nicht-eigenen belegten Lanes: Durchlauf i → i.
    • Erster Parent: die eigene Lane übernimmt seinen SHA → Kante lane → lane (oder Konvergenz zu bestehendem Parent).
    • Weitere Parents (Merge-Commits): neue oder vorhandene Lanes → Kante lane → targetLane.

CommitGraphView Views/CommitGraphView.swift

Jede Zeile rendert ihr eigenes Canvas. Die Höhe ist rowHeight = 56 pt; der Knoten liegt bei midY = height / 2.

  • Obere Hälfte (0 → midY): alle incoming-Kanten werden als gerade Linien (gleiche Lane) oder Bezier-Kurven gezeichnet.
  • Untere Hälfte (midY → height): analog für alle outgoing-Kanten.
  • Knoten: ausgefüllter Kreis (nodeRadius = 4 pt) bei (laneX, midY) über den Kanten.

Warum LazyVStack statt List?

macOS List (NSTableView-basiert) fügt intern Row-Insets und Abstände zwischen Zeilen ein. Diese Pixel-Lücken unterbrechen die Canvas-Linien benachbarter Zeilen visuell, selbst wenn die Zeichenlogik korrekt ist. Die Commit-Liste nutzt deshalb ScrollView + LazyVStack(spacing: 0) — damit liegen die Canvas-Instanzen pixelgenau aneinander, und alle Lane-Linien verlaufen lückenlos. Die Selektion wird manuell über .background + .onTapGesture abgebildet.

Persistenz & BookmarkStore

Datenmodell

Die Repository-Übersicht wird als indirect recursive Enum (BookmarkNode) modelliert: 

indirect enum BookmarkNode: Codable, Identifiable {
    case folder(id: UUID, name: String, children: [BookmarkNode])
    case repository(RepositoryBookmark)
}

Das indirect-Schlüsselwort erlaubt beliebig tiefe Verschachtelung bei voller Codable-Unterstützung durch den Swift-Compiler.

Speicherort

Die Repository-Liste wird als JSON-Datei im macOS Application-Support-Verzeichnis des Benutzers abgelegt: 

~/Library/Application Support/Git-Client/bookmarks.json

Der Pfad wird zur Laufzeit über FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask) ermittelt und ist damit unabhängig vom Installationsort der App. Das Verzeichnis Git-Client/ wird beim ersten Start automatisch angelegt.

Hinweis: Die Datei speichert ausschließlich Metadaten (Name, Pfad, Remote-URL, Benutzername) — niemals Passwörter oder Tokens. Credentials werden ausschließlich im macOS Keychain abgelegt (siehe Sicherheitskonzept).

BookmarkStore Persistence/BookmarkStore.swift

Liest und schreibt den BookmarkNode-Baum als JSON. Operationen: Laden beim App-Start, Speichern nach jeder Mutation (Hinzufügen, Umbenennen, Verschieben, Entfernen).

Atomares Schreiben

Um beschädigte Dateien bei einem Absturz während des Schreibvorgangs zu verhindern, verwendet BookmarkStore.save ein zweistufiges Verfahren:

  1. JSON wird in eine temporäre Datei (bookmarks.json.tmp) geschrieben.
  2. Die temporäre Datei ersetzt atomar die eigentliche Zieldatei via FileManager.replaceItem(at:withItemAt:).

Dadurch ist bookmarks.json zu jedem Zeitpunkt entweder vollständig im alten oder vollständig im neuen Zustand — nie halb geschrieben.

JSON-Format

Die Datei wird mit .prettyPrinted und .sortedKeys formatiert — lesbar für Menschen und stabil für Versionskontrollsysteme. Ein RepositoryBookmark-Knoten enthält:

FeldTypBedeutung
idUUID-StringStabiler Primärschlüssel; bindet Keychain-Einträge
nameStringAnzeigename im Bookmark-Browser
pathDateipfadAbsoluter Pfad zum lokalen Repository
remoteURLString?HTTPS-URL des Remotes (optional)
usernameString?Benutzername für HTTPS-Auth (optional, kein Passwort)

Lazy Loading der Commit-Liste

Motivation

Bei sehr großen Repositories (mehrere tausend Commits) wäre das vollständige Laden beim Öffnen zu langsam und speicherintensiv. Die App lädt deshalb zunächst nur eine konfigurierbare Anzahl von Commits (Batch) und lädt automatisch weitere nach, sobald der Nutzer ans Ende der Liste scrollt (Infinite Scrolling).

Paginierung via git log --skip

GitService.loadCommits(limit:skip:) verwendet das --skip-Flag von git log, um Seiten zu implementieren: 

// Erste Seite (Erstladung):
git log --all --date-order --pretty=format:… -2000

// Zweite Seite (nach Scrollen):
git log --all --date-order --pretty=format:… -2000 --skip=2000

--date-order sorgt für stabile Sortierung über alle Seiten hinweg, solange sich die Refs nicht verändern. --all schließt alle Branches und Remote-Tracking-Refs ein.

Paging-State im ViewModel

RepositoryViewModel verwaltet den Ladezustand mit drei Properties:

PropertyBedeutung
pagedCountAnzahl der per git log --skip bereits geladenen Commits (Basis für den nächsten --skip-Wert). Nicht identisch mit commits.count, da Branch-Tips, die außerhalb des Paging-Fensters lagen, separat nachgeladen werden.
canLoadMoreWird false, wenn eine Seite weniger als pageSize Commits zurückliefert — das Ende der Historie ist erreicht.
isLoadingMoreGuard gegen parallele Nachlade-Vorgänge.

Scroll-Trigger (Infinite Scrolling)

Am Ende der LazyVStack befindet sich ein unsichtbarer Indikator-View, der .onAppear nutzt, um loadMore() auszulösen. Da LazyVStack Kinder nur rendert, wenn sie im sichtbaren Bereich liegen, feuert .onAppear erst dann, wenn der Nutzer tatsächlich ans Ende scrollt. Sobald canLoadMore == false ist, verschwindet der Indikator und es werden keine weiteren Anfragen gesendet.

AppSettings & Einstellungen

Die Batch-Größe ist über das Einstellungsfenster (⌘,) konfigurierbar und wird in UserDefaults gespeichert.

KomponenteDateiDetail
AppSettings AppSettings.swift Zentraler Accessor für den UserDefaults-Key "commitBatchSize". Standardwert: 2000. Mindestwert: 100 (wird beim Lesen erzwungen).
SettingsView Views/SettingsView.swift macOS-Settings-Szene. Eingaben werden erst beim Klick auf Speichern übernommen. Wird das Fenster mit ungespeicherten Änderungen über den Schließen-Button geschlossen, erscheint ein Bestätigungs-Dialog.

Die Änderung der Batch-Größe greift beim nächsten Öffnen oder Neu-Laden eines Repositories. Laufende Ladevorgänge nutzen den Wert, der beim Start von load() aktiv war.

Drag & Drop

Der Bookmark-Browser basiert auf einem ScrollView mit rekursiv gerenderten BookmarkNodeView-Instanzen — nicht auf List { OutlineGroup }, das intern ein NSOutlineView verwendet.

Warum kein NSOutlineView?

NSOutlineView fängt Drag-Events ab, bevor sie das SwiftUI- Transferable-System erreichen. Jeder Versuch, NSItemProvider oder eigene UTTypes in einem List { OutlineGroup } zu verwenden, scheiterte daran, dass das NSOutlineView den Drag intern handhabte ohne die SwiftUI-Layer zu benachrichtigen.

Lösung: Transferable-basiertes Drag & Drop

  • .draggable(node.id.uuidString) auf jedem Knoten-View.
  • .dropDestination(for: String.self) auf jedem möglichen Ziel-View — nimmt die UUID des gezogenen Knotens an und ruft die entsprechende Move-Funktion im ViewModel auf.
  • Da String Transferable out-of-the-box erfüllt, entfällt jede UTType-Registrierung in Info.plist.

Sicherheitskonzept Credentials

Grundsätze

  • Kein Klartext in bookmarks.json — Passwörter und Tokens werden niemals in der Bookmark-Datei gespeichert.
  • Ausschließlich macOS Keychain — alle HTTPS-Credentials (Passwort/Token) landen im System-Keychain über die Security-Framework-API (SecItemAdd, SecItemCopyMatching, SecItemDelete).
  • Per Repository, nicht per Host — Credentials sind strikt an die bookmark.id (UUID) gebunden. Es gibt keine geteilten, host-basierten Credentials. Wer mehrere Repositories beim selben Host mit verschiedenen Accounts nutzt, erhält für jedes Repo einen eigenen Keychain-Eintrag.

Implementierung

KomponenteDateiAufgabe
KeychainStore Persistence/KeychainStore.swift Statische Methoden save(_:for:), load(for:), delete(for:). Service-Label: de.tobias.florian.Git-Client.credentials. Schlüssel: bookmark.id.uuidString.
CloneRepositoryView Views/CloneRepositoryView.swift SwiftUI-Sheet: Remote-URL, Benutzername, Passwort/Token — das Passwort wird nach dem Klonen sofort nach KeychainStore geschrieben und nicht länger im View-State gehalten.
GitService.clone(…) Services/GitService.swift Credentials werden transient per URL-Einbettung an git clone übergeben (https://user:token@host/…) und danach nicht persistiert.
GitService.fetch(…) Services/GitService.swift Analog zu clone: temporäre URL-Einbettung für git fetch --prune.

Keychain-Eintrag manuell löschen

Wird ein Repository aus dem Bookmark-Browser entfernt (Entfernen im Kontextmenü), löscht die App den zugehörigen Keychain-Eintrag nicht automatisch — das vermeidet unbeabsichtigte Datenverluste bei versehentlichem Löschen. Der Eintrag kann über die macOS-App Schlüsselbundverwaltung manuell gefunden und gelöscht werden (Suchbegriff: de.tobias.florian.Git-Client.credentials).
